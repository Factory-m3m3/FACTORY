What the code guarantees

ApexPad's Meme Coin Factory launches a token in a single transaction, writes its metadata into the token contract, then renounces all power over it inside that same transaction. This page shows where that is written, and what it does not cover.

Nothing is hidden — it is simply one click further than before, and that is exactly why it is written here rather than left to be discovered.

The previous factory's contracts are still online, unchanged, and the tokens they created have lost none of their guarantees: see the page dedicated to them.

01What this page proves

And, just as importantly, what it does not prove.

A memecoin launcher asks for enormous trust over an operation that lasts a few seconds: you sign a transaction, and a contract you did not write takes control of your token's entire supply. The only acceptable answer to that demand is to make trust unnecessary.

So this page asks you to believe none of my claims. Each one points either to a line of source code publicly verified on the explorer, or to a value you can read yourself on-chain, in a few clicks, with no terminal and no wallet connection.

The rule we hold ourselves to

Nothing is asserted here that a third party cannot check. Where a limit exists — and there are several — it is written as such, not glossed over. Section 12 is devoted entirely to them.

Said up front

These contracts are not audited. "Verified" on an explorer means the published source matches the deployed bytecode exactly. It does not mean an independent firm has reviewed it. The two words are used separately throughout this page, and never one for the other.

02The factory has no owner

Not "renounced": never had one.

Most launchers keep an admin able to change fees, pause things, redirect funds. The MemeCoinFactory contract has none of that. Its contract declaration is bare:

contract MemeCoinFactory {

No Ownable inheritance, no onlyOwner modifier anywhere in the file, no admin function at all. There is therefore no address in the world with any special power over this factory — not mine, not any other.

What is fixed is fixed for good, at deployment, as immutable values — burned into the bytecode, unreadable except by the code itself and impossible to rewrite:

Frozen valueWhat it is
UNISWAP_V3_FACTORYThe chain's official Uniswap v3 factory
POSITION_MANAGERThe official Uniswap v3 position manager
WETHThe chain's official WETH
SWAP_ROUTERThe official Uniswap v3 swap router
PLATFORMThe address receiving the platform 50% — see section 05
POOL_FEE = 10_000Uniswap v3 fee tier of 1% per swap
TICK_SPACING = 200The tick spacing imposed by that fee tier

You can see this without reading me: open the factory address on your chain's explorer (section 09), Read Contract tab. There is no owner() function — only reads: the immutables above, the tokenCount() counter, the allTokens() list, and the isLaunchedHere() registry from section 08. Write Contract tab: there is exactly one function, launchToken, and anyone can call it.

03One transaction, twelve steps

Everything succeeds together, or nothing exists.

launchToken() runs the whole sequence in one transaction. That is the central point: there is no gap between steps during which anyone — me included — could slip in.

  1. Token deployment — 100% of the supply is minted at once, to the factory, and the metadata (logo, description, links) is written in the constructor.
  2. Registration in isLaunchedHere — the token ↔ factory link is true from the instant the token exists, including for the rest of this transaction.
  3. Creation and initialisation of the Uniswap v3 pool, token/WETH, 1% tier.
  4. Reading the real tick computed by the pool itself — no in-house reimplementation of Uniswap maths.
  5. FeeSplitter deployment with creator = msg.sender, that is, you.
  6. LiquidityCustodian deployment, with its fee recipient already pointing at that FeeSplitter.
  7. Recording the pool in the token (setPool), before the mint — no window between the two.
  8. Minting the position, Uniswap v3, 100% single-sided, then explicit transfer of the NFT to the custodian.
  9. Sweeping token dust left on the factory to the FeeSplitter — not to some arbitrary address.
  10. Warm-up: a real buy then a real sell, in this same transaction. If they fail, the whole transaction reverts.
  11. Renouncing token ownership.
  12. Renouncing custodian ownership.
What the warm-up guarantees

Step 10 buys then sells back a small amount of the token before any renouncing. If the swap fails for any reason — malformed pool, invalid tick range, incompatible router — the entire transaction reverts and the token never existed.

Consequence: no stillborn token can come out of this factory. A token that exists is a token with on-chain proof that it was bought and sold at least once — in the very block of its creation, before anyone lost any power over it. The WETH recovered on the sell, minus both swap fees, is returned to the creator.

04Renouncing happens in the transaction

Not an intention announced for "later".

"Ownership renounced" is the easiest sentence to write in a whitepaper, and the easiest never to honour. Here it is not written in a whitepaper: it is written in the contract, two lines before the end of the launch function.

// 10. Renounce token ownership
token.renounceOwnership();

// 10bis. Renounce custodian ownership too
custodian.renounceOwnership();

Both calls are inside the body of launchToken(). They are not in a script to run later, nor in a function the creator would have to remember to call.

The verifiable consequence

For every token out of this factory, owner() returns 0x0000...0000 from its very first block of existence. There has never been a single block during which a human address controlled a token launched here.

Why the factory owns the custodian, and not you

At step 6, the custodian is created with the factory as owner — not the creator. That is not power retention, it is the opposite.

The only power a custodian owner has is changing the fee recipient. If the creator owned it, they could redirect 100% of the fees to themselves at any time and simply delete the platform share. And if the platform kept ownership, it could do the reverse at your expense.

So the factory holds it for a few instructions, then renounces at step 12, in the same transaction. Result: the fee recipient stays pointed at the FeeSplitter forever, and nobody — not you, not me, not the factory — can call setFeeRecipient() any more. The 50/50 rule becomes a property of the contract, not a commitment.

05The 50%, line by line

The easiest claim to betray on a launch platform.

Every launch deploys its own FeeSplitter contract, with two addresses frozen at construction and never modifiable afterwards:

FieldValueFrozen?
creatorThe address that signed launchToken() — youimmutable
platform0x3a7a125D23689d8F7f218B28f19305d33b6c9B18immutable

This platform address is the same one as under the previous factory: the factory change moved nothing on that side.

The split itself is three lines, and there is no other exit path for funds in this contract:

uint256 creatorAmount  = balance / 2;
uint256 platformAmount = balance - creatorAmount;

transfer(creator,  creatorAmount);
transfer(platform, platformAmount);
The precision that is missing everywhere else

On an odd balance, balance / 2 rounds down, so the platform receives 1 wei more than the creator. A wei is 0.000000000000000001 ETH. It is written here because "50/50" is false to the wei, and a proof page that rounds its own figures is worthless.

Nobody can withhold your share

release() is permissionless: anyone can trigger it, including you, including a stranger. The destinations, however, are frozen. So you depend on no action of mine to get your half — and I cannot hold it back.

Same upstream: collect() on the custodian, which pulls the fees accumulated in the Uniswap pool into the FeeSplitter, is also callable by anyone.

An example you can open right now

The first launch of the current factory, FORGE TEST FACTORY, produced the FeeSplitter 0xa6669197...cF33e950, verified "Exact Match" on Basescan. Its constructor arguments are displayed in the clear, at the bottom of the Contract tab:

Arg [0] creator_  : 0x0850a43B5EaEdBbbBdD317d0C030b83191dbdB56
Arg [1] platform_ : 0x3a7a125D23689d8F7f218B28f19305d33b6c9B18

A verifiable and non-trivial detail: that same FeeSplitter address exists identically on all eight chains, as do the token 0x715E215b…18652CE and the custodian 0x119C502a…AB972953 of that launch. It is not a coincidence — the address of a contract created by another contract depends only on the creating address and its counter. Same factory at the same address, same launch rank, therefore the same addresses. It is a mechanical consequence of the EVM, checkable on all eight explorers.

Three limits, stated plainly

The fees in question are Uniswap v3 swap fees (1% per trade). If there is no volume, there are no fees — 50% of zero is still zero. This factory does not create volume.

creator is frozen. If you lose the key of the address that signed the launch, your share becomes unreachable, permanently, for everyone.

Fees stay in the pool until collect() is called, then in the FeeSplitter until release() is called. Neither fires on its own.

06Liquidity cannot come back out

Verifiable by absence of code, not by commitment.

The Uniswap v3 position NFT is held by the launch's LiquidityCustodian. That contract can do three things, and three only: receive the position once, collect accumulated fees, and change the fee recipient while it has an owner — which, as we saw, stops inside the launch transaction. It also exposes a public read, currentLiquidity(), which changes nothing.

What matters here is not what it does, but what it does not contain:

FunctionPresent?Consequence
decreaseLiquidity()AbsentLiquidity cannot be reduced
burn()AbsentThe position cannot be destroyed
Outgoing NFT transferAbsentThe position cannot leave the contract
selfdestructAbsentThe contract cannot disappear
Proxy / upgradeAbsentThe code cannot be replaced

A guarantee by absence is stronger than a guarantee by promise: it depends on no future behaviour. The public currentLiquidity() function lets anyone read the position's liquidity at any time and confirm that it never goes down.

What "locked liquidity" does NOT mean here

The position is 100% single-sided: at launch, only the token's entire supply is deposited into the pool. No ETH is deposited by the creator or by the platform. The ETH in the pool is the buyers', arriving purchase by purchase.

Concretely: there is no "treasury" backing a price floor, and some scanners will show "LP locked: 0%" because they look for LP tokens locked with a third-party service, which is not the mechanism used here.

On the other hand — and this is the point — that accumulated ETH cannot be taken out by anyone other than sellers themselves, by selling into the market. Neither the creator nor I can pull it from the pool: the only function that would allow it, decreaseLiquidity(), does not exist in the contract holding the position.

07The token: no mint, no tax

A deliberately boring ERC-20.

The MemeToken contract deployed at each launch is a standard ERC-20, with no overlay. The total supply is minted once, in the constructor, and stored as immutable.

Usual mechanismPresent?
Mint function after deploymentNone
Buy or sell taxNone
Address blacklist / whitelistNone
Transfer pauseNone
Maximum amount per walletNone
Delay between two transactionsNone

None of these is disabled by configuration: the transfer logic is simply not overridden. Standard ERC-20 transfer applies, without a single condition tied to the pool, the clock or the block number.

Apart from the ownership functions themselves, the only owner-restricted function this token ever had is setPool(), which records the pool address once and for all, purely for information — and it is called at step 7, before the position mint and well before the renouncing. Afterwards, nobody can call it.

A deliberate absence: no anti-sniping

There is intentionally no anti-bot delay at launch. Two reasons, and the first is the less flattering one: a fixed delay protects nobody. Once the countdown ends, a bot is still faster than a human — the delay moves the race, it does not cancel it.

The second: those temporary transfer-blocking mechanisms trigger "honeypot" false positives on several scanners, which damages the contract's readability for a careful buyer. We preferred a contract anyone can read in full over a protection that is not one.

08Metadata lives in the contract

This is the entire reason the factory deployed on 12 September 2026 exists.

A memecoin coming out of a launcher almost always arrives naked at the aggregators: no logo, no description, no links, and no way to tell where it came from. All of that is then submitted by hand, form after form, by someone with nothing to prove they are the creator.

The current factory writes that information into the token contract, in the constructor, inside the launch transaction. It is readable by anyone, without going through our pages, and the factory renounces ownership of the token in that same transaction: there is no window during which anyone could rewrite it.

One function, in the Pons launchpad format

The signature is taken character for character from the Pons launchpad's, which Mobula and Bitquery already know how to decode. That is deliberate, and it is the whole point: an integrator has no decoder to write, they add our factory address to their existing adapter.

function getTokenInfo() external view returns (
    address tokenDeployer,
    string  memory tokenLogo,
    string  memory tokenDescription,
    Socials memory tokenSocials
);

struct Socials { string twitter; string telegram; string discord; string website; string farcaster; }

The link goes both ways

It is this pair that lets anyone attribute a token to a launchpad without relying on an off-chain claim:

  • the token names its factory: MemeToken.factory(), immutable, set in the constructor;
  • the factory confirms the token: MemeCoinFactory.isLaunchedHere(token) returns true.

Both must agree. A contract claiming to come from here without being registered gives itself away in one call — and vice versa.

What the contract refuses to write

FieldRule enforced by the contractWhy
tokenLogoar:// or ipfs:// only, 256 bytes max. https:// is rejected.An https URL can silently change its content after launch. A content-addressed identifier can only die, never change — and dying is recoverable: anyone can re-host the same bytes under the same identifier.
Socialshttps:// only, 256 bytes max, case-sensitive (HTTPS:// is rejected)These strings are injected back into <a href> tags by the catalogue and the proof pages. Without this guard, a javascript: or data: URI would mean script execution on our own pages — and on those of any consumer of this data.
tokenDescription512 bytes maxA cost bound: the field is stored on-chain, on eight chains including Ethereum.
Optional, but permanent

All of these fields can be left empty at launch. But since nothing can be modified afterwards, empty at launch means empty forever. It is written on the launch form, and it is repeated here.

And one thing that cannot be glossed over: the contract guarantees this information will never change. It does not guarantee that it is true. Nobody checks that a Telegram link leads anywhere, or that a description states anything accurate. See section 12.

What that confirmation covers, and what it names

The classification of the domain apexpad.io does not depend on any contract address: it therefore applies to the current factory too, and it is what governs the warning a wallet shows at signing time.

Field evidence, which says more than a letter: the nine launches made with the current factory — one per chain, except Robinhood Chain, where two were made — triggered no wallet warning at all. That is exactly the test described below, and it checks out.

The one caveat, for accuracy: the written exchange of 17 August names the address 0xa33F5330...e87049C8, not 0xB7DA71D5...1cb1A75c, which did not yet exist at that date. The two previous-generation factories on Polygon (0x40D61104...0CCE3cDC) and Robinhood Chain (0xcD5492aC...793C3f96) are not named either, for the same reason: distinct addresses.

The test you can redo yourself

A copy of an email proves nothing: it can be forged in three minutes. The check that matters is within your reach and does not depend on my word — open the launch tool and connect your wallet. No "deceptive request" or "untrusted site" warning should appear. That is observable live, right now.

Three caveats, because they matter

Blockaid is not an auditor and does not present itself as one. "Benign" means no known malicious pattern was detected, not that the code was reviewed line by line. Section 12 remains entirely valid.

The technical description in that ticket is mine, not a Blockaid conclusion: it is the body of my report, quoted as-is in the thread. The facts it states are accurate and verifiable — sections 02 to 08 show you where — but they were not validated one by one by Blockaid.

A classification is not permanent. It can be revised at any time, in either direction. That is why the date appears above rather than a logo.

12What remains on you

The most important section of this page.

Everything above is about one thing: what the code prevents. Here, in the same spirit, is what it does not prevent.

These contracts are not audited

They are verified on eight explorers, which guarantees that the code you read is the code that runs. No independent firm has reviewed them. The source file itself carries the NOT AUDITED notice at the top, and the launch interface displays it. A bug remains possible, including one that would falsify one of the guarantees above. You have my good faith and the code — not a third party's signature.

Metadata is frozen, not verified

Section 08 guarantees that a logo, a description and links written at launch can never be modified again. It never guarantees that they are accurate. Nobody checks that a link leads anywhere, that a name does not copy another project's, or that a description is anything other than fiction. Immutable, false metadata stays false, permanently.

A memecoin can be worth zero

None of the guarantees on this page concern price. Liquidity that cannot be withdrawn is not liquidity that supports a price. A token launched here can lose all its value, and most do.

The factory does not vet projects

The name, ticker, supply and starting market cap are chosen freely by whoever launches. Nothing is checked: not the originality of the name, not the existence of a team, not any intention whatsoever. A token launched by this factory is not endorsed by ApexPad. The mechanism is sound; what the creator does with it afterwards is not up to us.

The creator keeps their token — and can sell it

The step-10 warm-up returns their WETH, and nothing stops them buying their own token on the market like anyone else. What the contract guarantees is that they receive no free allocation at creation: the entire supply goes into the pool, bar rounding dust, which is itself swept to the FeeSplitter at step 9 and therefore split 50/50 like any other fee. What they buy afterwards, they buy at market price, visible on-chain to everyone.

Never send ETH directly to the factory

The factory accepts native ETH, because it must be able to receive it during the warm-up. It has no withdrawal function. ETH sent directly to its address, outside a call to launchToken(), would stay stuck there forever — including for me. Always go through the launch interface.

The 50% depends on a key only you hold

Already said in section 05, repeated here because it is irreversible: the creator share is locked to the address that signed the launch. Lost, it is lost for everyone.

13Check it yourself, in 7 clicks

No terminal, nothing to install, no wallet to connect.

Take any token from the catalogue and its proof page, which gives you its addresses. Then, on its chain's explorer:

  1. The factory — open its address (section 09), Contract tab. You should see the green verification tick and the full source. Scroll down: the constructor arguments show _platform = 0x3a7a125D...3b6c9B18.
  2. Still the factory, Read Contract tab. Go through the list: there is no owner(). Write Contract tab: there is only launchToken.
  3. The two-way link — on the factory, isLaunchedHere with the token address: true. Then on the token, factory(): the factory address. The two must agree.
  4. The token — Read Contract tab, owner(). Expected answer: 0x0000000000000000000000000000000000000000. Then getTokenInfo(): the logo, description and links, exactly as written at launch.
  5. The custodian — same thing. owner() returns 0x0000...0000, and feeRecipient() returns the FeeSplitter address of that same launch. Nobody can change it any more.
  6. The FeeSplitter — Read Contract, then creator() and platform(). The first is the address that launched the token, the second is the platform address, identical for every launch.
  7. The Uniswap position — look up the position id from the proof page on the chain's NonfungiblePositionManager: its holder is the custodian. Then, on the custodian, currentLiquidity(): come back and read it whenever you like, it will never go down.
If a single one of these seven points does not check out

Then this page is lying, and you have public proof of where. Say so publicly. That is exactly the point of writing proofs rather than promises: they are refutable.
